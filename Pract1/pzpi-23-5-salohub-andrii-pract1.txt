3 ОПИС ВИКОНАНОЇ РОБОТИ

     Ланцюжок Обов’язків (Chain of responsibility) – поведінковий шаблон проектування, який дозволяє уникнути жорсткої прив’язки відправника запиту до отримувача. Всі можливі обробники запиту утворюють ланцюжок, а сам запит переміщається цим ланцюжком. Кожен об’єкт у цьому ланцюжку при отриманні запиту вибирає або закінчити обробку запиту, або передати запит на обробку наступному по ланцюжку об’єкту.
     Головна мета шаблону - розрив жорсткого зв'язку між відправником запиту та його отримувачами. Замість того, щоб відправник знав конкретний об'єкт, який має обробити запит, він передає його "ланцюжку". Кожен об'єкт у ланцюжку має можливість або обробити запит самостійно, або передати його далі наступному компоненту.
     Це дозволяє динамічно визначати, хто саме відповідатиме за запит, залежно від його типу або вмісту.
     Як працює шаблон:
1. Уніфікований інтерфейс: Створюється загальний інтерфейс для всіх обробників, який зазвичай містить метод handle(request) та метод для встановлення наступного обробника в ланцюжку.
2. Зв’язний список: Обробники з’єднуються один з одним, утворюючи структуру, схожу на однозв'язний список. Кожен обробник зберігає посилання на "наступного".
3. Логіка обробки: Коли запит надходить до обробника, той виконує перевірку:
• Якщо він може обробити цей запит - він це робить (і, залежно від логіки, або зупиняє ланцюжок, або передає далі);
• Якщо не може - він автоматично перенаправляє запит наступному об’єкту.
   
4. Завершення: Якщо запит пройшов через весь ланцюжок і не був оброблений, він або ігнорується, або викидається виключення (залежно від реалізації).

     Шаблон варто використовувати у таких випадках:
• Кілька потенційних обробників: Коли програма має обробити запит різними способами, але заздалегідь невідомо, який саме тип запиту надійде і який обробник знадобиться (наприклад, система фільтрації логів або обробка подій GUI);
• Динамічна зміна обробників: Якщо набір об’єктів, здатних обробити запит, повинен змінюватися під час виконання програми;
• Послідовна перевірка: Коли запит має пройти через серію обов’язкових етапів (наприклад, ланцюжок Middleware в Express.js або NestJS: перевірка авторизації, валідація даних, кешування, логування).

     Використання шаблону «Ланцюжок обов’язків» дає розробнику значну гнучкість, оскільки воно дозволяє реалізувати принцип єдиної відповідальності на практиці. Замість одного величезного методу з купою перевірок, ви отримуєте набір маленьких, незалежних класів, кожен з яких фокусується на конкретній задачі. Це суттєво спрощує підтримку коду, адже ви можете додавати нові етапи обробки або змінювати їхній порядок, не зачіпаючи логіку клієнта чи інших обробників. Крім того, такий підхід забезпечує слабку зв’язність системи: відправник запиту взагалі не знає, хто саме і як його обробить, що робить архітектуру чистішою та адаптивнішою до змін.
     Водночас цей шаблон має і свої підводні камені, про які варто пам'ятати під час проектування. Найголовніший ризик полягає у тому, що запит може залишитися взагалі не обробленим, якщо він пройде крізь увесь ланцюжок і жодна ланка не візьме його "на себе", а дефолтний сценарій не був передбачений. Також варто враховувати питання продуктивності: якщо ланцюжок стає занадто довгим, виконання запиту сповільнюється, оскільки він має пройти через безліч перевірок, перш ніж потрапить до потрібного місця. Нарешті, такий підхід може ускладнити відстеження логіки виконання та дебаг, оскільки прямий зв'язок між причиною і результатом розмивається, і іноді буває важко зрозуміти, на якому саме етапі запит був змінений або зупинений.
     Тепер перейдемо до розгляду прикладів реалізації шаблону в коді. Першим ми розберемо абстрактний приклад, на якому можна чітко побачити механіку передачі запиту між об’єктами та зрозуміти базову ієрархію класів.
     В основі реалізації лежить базовий клас, який забезпечує зв’язність елементів. Для формування черговості обробників використовується метод setNext, який зберігає посилання на наступний об’єкт у ланцюжку (рядки 1-5).
     Базова логіка передачі запиту визначена у методі handle абстрактного класу. Якщо поточний об’єкт не має специфічної логіки обробки, він автоматично перенаправляє запит далі за наявності наступного обробника (рядки 8-10). Якщо ж ланцюжок завершується, повертається дефолтне повідомлення про завершення процесу (рядок 11).
1  class AbstractHandler {
2    setNext(handler) {
3      this.nextHandler = handler;
4      return handler;
5    }
7    handle(request) {
8      if (this.nextHandler) {
9        return this.nextHandler.handle(request);
10      }
11      return 'Request processed';
12    }
13 }
     
     
     Конкретні реалізації, такі як MonkeyHandler та DogHandler, демонструють вибіркове виконання завдань. У класі MonkeyHandler виконується перевірка типу запиту: якщо він відповідає значенню "Nut", обробник виконує дію самостійно (рядки 17-19). В іншому випадку, за допомогою виклику super.handle(request), запит делегується базовому класу для подальшої передачі по ланцюжку (рядок 20). Аналогічна логіка реалізована і для DogHandler щодо м’ясних кульок (рядки 26-30).
15 class MonkeyHandler extends AbstractHandler {
16   handle(request) {
17     if (request === 'Nut') {
18       return `Monkey: I'll eat the ${request}.`;
19     }
20     return super.handle(request);
21   }
22 }
23
24 class DogHandler extends AbstractHandler {
25   handle(request) {
26     if (request === 'MeatBall') {
27       return `Dog: I'll eat the ${request}.`;
28     }
29     return super.handle(request);
30   }
31 }


     Процес ініціалізації системи починається зі створення екземплярів обробників (рядки 33-34) та їхнього логічного поєднання в єдину структуру (рядок 36). При виклику методу handle на першому елементі, система демонструє три різні сценарії:
• Миттєва обробка першою ланкою (рядок 38).
• Транзит запиту через мавпу до собаки, яка і виконує обробку (рядок 39).
• Повний прохід крізь ланцюжок без знаходження цільового обробника, що завершується базовою відповіддю (рядок 40).

33 const monkey = new MonkeyHandler();
34 const dog = new DogHandler();
36 monkey.setNext(dog);
38 console.log(monkey.handle('Nut'));
39 console.log(monkey.handle('MeatBall'));
40 console.log(monkey.handle('Banana'));


     Далі розглянемо більш прикладний кейс, який демонструє використання шаблону для побудови системи Middleware. У цьому прикладі ланцюжок використовується для послідовної перевірки прав доступу та логування подій у веб-додатку.
     На відміну від попереднього прикладу, де обробники вибирали одну конкретну дію, тут демонструється модель фільтрації та послідовного проходження. Клас AuthHandler виступає в ролі "вартового": він перевіряє наявність даних користувача в об'єкті запиту (рядки 17-19). Якщо користувач відсутній, ланцюжок переривається і повертається повідомлення про помилку (рядок 18), що запобігає виконанню подальших, можливо, "дорогих" операцій.
15 class AuthHandler extends AbstractHandler {
16   handle(request) {
17     if (!request.user) {
18       return 'Unauthorized';
19     }
20     return super.handle(request);
21   }
22 }


     Клас LoggingHandler ілюструє тип обробника, який виконує допоміжну дію (фіксацію URL запиту в консолі), але не зупиняє процес (рядки 26-27). Через виклик super.handle(request) він обов'язково передає керування наступній ланці або завершує виконання, якщо він останній у списку (рядок 27).
24 class LoggingHandler extends AbstractHandler {
25   handle(request) {
26     console.log(`Request for ${request.url}`);
27     return super.handle(request);
28   }
29 }

     
     Процес ініціалізації утворює логічну послідовність: спочатку безпека, потім моніторинг (рядок 34). При аналізі результатів виконання можна побачити два критичні сценарії:
• Переривання: Коли запит не містить користувача, AuthHandler повертає "Unauthorized", і логування у другому обробнику навіть не викликається (рядок 36).
• Повний прохід: Коли запит валідний, він проходить крізь AuthHandler до LoggingHandler, де виводиться лог, а потім повертається фінальний статус успішної обробки (рядок 37).

     На завершення розглянемо, як теоретична концепція «Ланцюжка обов’язків» трансформується у реальний стандарт сучасної веб-розробки (код наведено в додатку В.1). У таких фреймворках, як Express, Koa або NestJS, цей патерн є фундаментом обробки HTTP-запитів. Замість одного величезного контролера, запит проходить через «конвеєр» спеціалізованих функцій, які називаються Middleware.
     У цій реалізації об’єкти req та res виступають у ролі контейнерів даних, що передаються ланцюжком. Ключовим елементом керування є функція next() - це фактично реалізація виклику наступного обробника, яку ми бачили в абстрактному прикладі.
• Транзитний обробник: Глобальна функція логування (рядки 6–9) виконує свою дію і обов'язково викликає next() (рядок 8), передаючи запит далі незалежно від його змісту;
• Умовна обробка: Функція checkAuth демонструє можливість зупинки ланцюжка. Якщо заголовок авторизації відсутній, вона відправляє відповідь клієнту самостійно (рядок 16) і не викликає next(). Це миттєво припиняє рух запиту по конвеєру.
• Композиція ланцюжка: Виклик методу app.get (рядок 21) наочно показує, як ми можемо динамічно конструювати ланцюжок для конкретного маршруту, просто перелічуючи обробники один за одним.

     Назва інструменту та версія: Gemini 3.1 Pro
     Мета використання: аналіз архітектурних рішень та оцінка їхнього впливу на якость програмного забезпечення.
     Внесок автора: перевирих технічну коректность термінів та логічних зв'язків у запропонованому аналізі.
     Такий підхід дозволяє розробникам будувати складні системи з дуже простих "цеглинок", де кожен Middleware відповідає лише за одну операцію: перевірку токена, парсинг JSON, стиснення даних або логування, що і є головною перевагою Chain of Responsibility.
     Впровадження паттерна Chain of Responsibility (Ланцюжок відповідальності) кардинально змінює архітектурний ландшафт додатку, переходячи від жорсткої, монолітної логіки прийняття рішень до децентралізованої та модульної моделі. Головний архітектурний вплив полягає в послабленні зв’язності (loose coupling): об'єкт, що надсилає запит, взагалі не знає, хто саме його обробить і скільки ланок пройде цей запит. Це дозволяє проектувати компоненти як ізольовані модулі, що спеціалізуються на одному вузькому завданні, що ідеально відповідає принципу єдиної відповідальності.
     Назва інструменту та версія: Gemini 3.1 Pro
     Мета використання: узагальнення теоретичних відомостей про архітектурні патерни та формулювання висновків щодо їхнього системного впливу на розробку програмного забезпечення.
     Внесок автора: перевірив логічну послідовність висновків.
     


4 ВИСНОВКИ

     Шаблон «Ланцюжок відповідальності» є фундаментальним інструментом для створення гнучких та адаптивних архітектур, що дозволяє мінімізувати прямі зв'язки між об'єктами, які ініціюють запити, та тими, що їх безпосередньо виконують. Такий підхід забезпечує високий рівень інкапсуляції логіки та дозволяє системі еволюціонувати без необхідності модифікації клієнтського коду, що робить загальну побудову програмного продукту значно стійкішою до змін та простішою у підтримці.
     Незважаючи на значні переваги в контексті дотримання принципів єдиної відповідальності та відкритості до розширення, використання цього патерну вимагає ретельного проектування для уникнення ризиків, пов'язаних із втратою запитів або створенням надмірно довгих ланцюжків, які важко відстежувати. Важливо розуміти, що гнучкість, яку надає цей шаблон, привносить певну складність у налагодження потоку виконання, тому він може бути неефективним при складній фільтрації, якщо ланцюжок довгий і більшість обробників не виконує корисної роботи.
