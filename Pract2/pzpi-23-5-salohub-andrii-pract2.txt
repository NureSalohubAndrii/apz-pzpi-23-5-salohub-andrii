2 ЗАВДАННЯ     Метою роботи є дослідження архітектури складної програмної системи та аналіз застосованих архітектурних підходів.     У межах роботи необхідно:• виконати аналіз архітектури програмної системи;• визначити архітектурний стиль;• описати основні компоненти;• проаналізувати взаємодію підсистем;• оцінити масштабованість та переваги архітектурних рішень;• підготувати презентацію та відеодоповідь;• оформити звіт відповідно до ДСТУ 3008:2015.
3 ОПИС ВИКОНАНОЇ РОБОТИ     На початку свого існування Uber був побудований як монолітна система: єдина кодова база, один сервер бази даних та проста логіка. Проте зі стрімким зростанням кількості користувачів, водіїв та географії покриття, така архітектура перестала справлятися з навантаженням.     Сьогодні архітектура Uber - це глобально розподілена система, розрахована на обробку мільйонів транзакцій та подій у реальному часі. Головний виклик платформи - це робота з динамічними геопросторовими даними: постійне оновлення координат водіїв (кожні кілька секунд) та миттєвий пошук найближчої вільної машини. Для вирішення цих завдань система використовує підхід агрегації та обробки потоків даних на льоту, розбиваючи глобальну карту на дрібні географічні зони.     Сучасна архітектура Uber розроблена для вирішення трьох головних викликів:• Висока доступність (High Availability): Система не може мати простоїв, адже це означає пряму втрату грошей і довіри користувачів.• Низька затримка (Low Latency): Відстеження геолокації та метчинг (пошук пари "водій-пасажир") мають відбуватися в реальному часі.• Глобальний масштаб: Обробка мільйонів запитів одночасно у різних куточках світу.Назва інструменту та версія: Gemini 3.1 Pro.     Мета використання: з'ясувати призначення та роль API Gateway Pattern в мікросервісній архітектурі, зокрема його функцію як єдиної точки входу для мобільних додатків.     Внесок автора: проаналізував пояснення принципу роботи API Gateway, виокремив його ключові переваги (маршрутизація, безпека, балансування навантаження).     Сучасний Uber базується на мікросервісній архітектурі (Microservices Architecture). Замість одного великого застосунку, система складається з тисяч незалежних сервісів, кожен з яких виконує вузькоспрямовану функцію.     Додатково застосовуються такі архітектурні патерни:• Подієво-орієнтована архітектура (Event-Driven Architecture): Використовується для асинхронної обробки (наприклад, зміна статусу поїздки генерує подію, на яку реагують сервіси оплати та сповіщень);• API Gateway Pattern: Усі запити від мобільних клієнтів проходять через єдині шлюзи, які маршрутизують їх до відповідних внутрішніх мікросервісів.Назва інструменту та версія: Gemini 3.1 Pro.     Мета використання: отримати детальний опис принципу роботи Dispatch Service та зрозуміти його місце в мікросервісній архітектурі.     Внесок автора: проаналізував згенерований текст, та отримав розуміння логіки метчингу.     Архітектуру системи можна умовно розділити на кілька критичних блоків:• Клієнтські додатки (Rider App та Driver App): Точки взаємодії з користувачами, які постійно надсилають дані про геолокацію та стан.• API Gateway / WebSockets Server: Шар, що забезпечує постійне з'єднання між мобільними телефонами та серверами для обміну даними у реальному часі.• Dispatch Service: Серце Uber. Він відповідає за метчинг (matching) - пошук та з'єднання вільного водія з пасажиром на основі їхнього розташування.• Location Service: Збирає, обробляє та зберігає мільйони GPS-координат щосекунди. Для індексації локацій використовується бібліотека Google S2 Geometry, яка ділить карту Землі на комірки для швидкого пошуку об'єктів у заданому радіусі.• Routing / Map Service: Відповідає за побудову маршруту, врахування заторів та розрахунок орієнтовного часу прибуття за допомогою алгоритмів на графах.• Trip Management Service (Менеджер поїздок): Відстежує життєвий цикл поїздки.• Payment Service: Обробляє фінансові транзакції, взаємодіє зі сторонніми платіжними шлюзами.• Бази даних: Cassandra - для швидкого запису високочастотних даних (наприклад, GPS-трекінг). PostgreSQL - для транзакційних та реляційних даних (профілі користувачів, налаштування). Redis - для кешування найчастіших запитів.     Взаємодія компонентів у системі побудована на принципах високої швидкості та відмовостійкості, що досягається поєднанням синхронних і асинхронних підходів до комунікації. Внутрішні мікросервіси взаємодіють між собою за допомогою синхронної комунікації у вигляді віддалених викликів процедур (RPC), використовуючи високоефективні фреймворки, такі як gRPC або власний TChannel. Це забезпечує мінімальні затримки та швидку обробку запитів у критичних частинах системи.     Паралельно з цим застосовується асинхронна взаємодія через брокери повідомлень, зокрема Apache Kafka. Такий підхід дозволяє розвантажити основні сервіси та підвищити стійкість системи. Наприклад, після завершення поїздки Trip Service публікує відповідну подію в Kafka, після чого інші сервіси, такі як сервіс рейтингів, надсилання електронних чеків або платіжний сервіс, підписуються на цю подію і незалежно виконують свої функції без блокування основного процесу.     Взаємодія з клієнтськими застосунками організована через довготривалі з’єднання за допомогою WebSockets, що дає змогу передавати дані в режимі реального часу. Завдяки цьому користувачі можуть спостерігати за рухом автомобіля на карті без необхідності постійного оновлення інтерфейсу, що значно покращує користувацький досвід.     Діаграма на рис. 1 відображає описану раніше архітектуру, на верхньому рівні розташовані мобільні пристрої користувачів, які представлені додатками для пасажирів та водіїв на базі iOS та Android, що взаємодіють із системою через протоколи HTTPS для стандартних запитів та WebSockets для підтримки зв'язку в реальному часі. Весь вхідний трафік проходить через єдину точку входу у вигляді API Gateway, який відповідає за автентифікацію користувачів, маршрутизацію запитів та балансування навантаження між внутрішніми ресурсами. Центральне місце в архітектурі займає кластер мікросервісів, тут наведені не всі, але основна частина та за що вони відповідають було описано вижче. Нижній рівень системи складається з інфраструктурних компонентів для обробки та зберігання даних. Для управління потоками повідомлень і подій у реальному часі використовується шина даних Apache Kafka. Бази даних розділені за призначенням: Cassandra обробляє високочастотні записи GPS-координат, PostgreSQL зберігає структуровану інформацію про користувачів, поїздки та платежі, а Redis виконує роль кешу для швидкого доступу до сесій. На завершення система інтегрується з зовнішніми сервісами через HTTPS, де Stripe обробляє платежі, Twilio відповідає за комунікації, а Firebase використовується для доставки сповіщень на мобільні пристрої.Рисунок 1 – UML діаграма розгортання для Uber     Перехід до мікросервісів та розподілених систем забезпечив Uber низку критичних переваг:• Горизонтальне масштабування: Якщо навантаження на сервіс платежів зростає (наприклад, у свята), розробники можуть додати сервери лише для цього сервісу, не чіпаючи решту системи.• Відмовостійкість (Fault Tolerance): Ізоляція процесів гарантує, що якщо сервіс розсилки чеків на email впаде, функція замовлення таксі та геометчинг продовжать працювати без збоїв. Додаток просто приховає тимчасово недоступний функціонал (Graceful Degradation).• Висока пропускна здатність даних: Використання Apache Kafka дозволяє бекенду обробляти терабайти телеметрії та GPS-даних щодня без блокування баз даних.• Ефективність геолокації: Індекс H3 замінив складні обчислення відстаней між точками на прості операції пошуку в словнику (який водій у якому шестикутнику), що зменшило навантаження на сервери у десятки разів і забезпечило мілісекундні затримки при пошуку авто.
4 ВИСНОВКИ     Підсумовуючи проведене дослідження, можна стверджувати, що архітектура програмної системи Uber є яскравим прикладом успішної еволюції від базового монолітного рішення до глобальної, високонавантаженої та розподіленої мікросервісної платформи. Головним викликом для системи стала необхідність миттєвої обробки гігантських масивів динамічних геопросторових даних, що було успішно вирішено завдяки впровадженню подієво-орієнтованих підходів, асинхронної взаємодії компонентів та поєднанню різних типів баз даних.  Застосування таких передових рішень, як геопросторове шардування та незалежне горизонтальне масштабування мікросервісів, дозволило системі гарантувати безперебійну роботу, гнучкість, високу відмовостійкість та здатність локалізувати технічні збої. Таким чином, детальний аналіз підтвердив, що саме грамотно скомбіновані архітектурні патерни є надійним фундаментом, який забезпечує життєздатність та безмежний потенціал до масштабування сучасних складних програмних комплексів.
